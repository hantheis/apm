## Findings that shape the port

- **Status is a fixed vocabulary.** Raised by Hannah on ticket 01. The contract now makes each tracker declare its `done_statuses`; protocol code never names a literal status. Buganizer slots in by declaration.
- **The agent has no identity of its own on Linear.** Every write through the connector is attributed to the operator, so agent comments carry the signature line `-- apm` and the idempotency rule reads the signature, not the author. **Buganizer writes as the agent's own identity** (confirmed by Hannah, 2026-09-12), so at port time: set the agent author name to that identity, drop the signature from posted comments, and keep author-based detection. `Comment.is_agent` already accepts either, so the change is one line in `sign` plus the identity name. Keep the signature on Linear.
- **Labels are applied, never created, by the boundary.** Creating them is an operator step. Corporate hotlists may need an admin.
- **Native hierarchy and blocked-by are convenience.** Linear has both; Buganizer has blocked-by and (via hotlists or parent bugs) a hierarchy. The text copies in the proposal comment and the brief remain authoritative.

## Open at port time

- How strictly a context pack bounds reads beyond its named sources (design summary, deliberately deferred; restated in `context-pack-format.md`). v1: inputs come from the pack or the issue's own links, and nothing from another pack leaks out; unlisted documents inside the same client are not blocked.
- Whether Buganizer's assign-to-agent machinery replaces the execute-task shell entirely (design summary says yes; confirm on first real task). **Working position, 13 September 2026 (Hannah):** yes. Hannah files the short intake under the project bug and assigns it to the agent; that assignment is the trigger, as "agent ready" is in the workflow this borrows from. Assignment then means *triage, and if agent-capable carry straight on to execution*: too thin posts questions and stops; too big posts the proposal and waits for approve; human-only posts the context brief and stops. The pause between the full brief and the work is dropped for small tasks and kept for splits. Whether the assigned agent follows this unaided or needs a short Antigravity workflow file depends on how the files are set up on the corporate side; decide when the file layout is known.
- Whether the brief-text copy of dependencies can be dropped once Buganizer's blocked-by is in use (spec says maybe).
- ~~What carries the project marker in Buganizer.~~ **Decided 13 September 2026 (Hannah):** Buganizer's hierarchy. Tasks are nested under a project bug, so the pack slug comes from the parent chain: walk up to the top-level project bug and map it to a slug in `trackers/buganizer.md` (one table row per project: bug id, pack slug). `project_slug` in `apm/context.py` then reads that field instead of a label; sub-issues inherit by construction, since they are created under the same parent. Nothing else changes: the pack files, the isolation check, and the `project:` line in the intake template (which becomes "file it under the project bug") stay as they are.
- Google Docs artifact store setup: folder designation, write access, Doc-comment reading (`stores/google-docs.md`). **Access confirmed in principle, 13 September 2026 (Hannah):** the Antigravity agent identity can read and write Drive folders. Steps 1 to 3 of the store's setup (designate the folder, share it, write check) still run at port time to record the folder id and the date.
- **Agent credentials** (ticket 18). In v1 the executing agent holds none of its own: it runs inside the operator's Claude Code session, reads through the operator's connectors, and comms are drafts, so nothing needs a login the operator does not already have. At the port the Antigravity agent has its own identity, so three things become decisions: which of a context pack's Sources it can read under that identity (`context-pack-format.md`, Sources, and the read-strictness question above), whether it can write to the deliverables folder (`stores/google-docs.md`, write access), and where any secret it does need lives and who rotates it. The core stays silent on this by design; record the answer here and in the pack's Sources column, never in a brief or an issue. Ticket 13's end-to-end run happened on Linear with the local-files store (below). **Answered 13 September 2026 (Hannah):** the Antigravity agent identity can read from and write to Drive folders, so the first two decisions are settled (pack Sources on Drive are readable under that identity; the deliverables folder is writable). The third, where any other secret lives and who rotates it, stays open until a source outside Drive is needed.

**Gaps between local-tracker and Linear behaviour, with proposed fixes** (nothing patched in the Linear boundary alone):

1. *Pre-existing issues are candidates.* The protocol's candidate rule (any not-done issue without an agent comment) would have swept Lasso's onboarding boilerplate (`LAS-1` to `LAS-4`), two hand tests (`LAS-5`, `LAS-6`) and the ticket 03 throwaways (`LAS-7`, `LAS-8`). A local issue directory only ever holds issues meant for the system, so this never showed. This run scoped the pass by hand to the three filed issues. Proposed fix, in the protocol: a candidate must carry a `project:` label or the operator must name a default pack for the pass; issues with neither are listed in the digest under "unscoped" and not touched. Applies to every tracker.
2. *`project:` labels do not exist on Lasso.* The boundary never creates labels, and the setup checklist's label step names only the eight `apm:` labels. When Hannah answers question 1 the boundary cannot apply `project:<slug>` until she creates it. Proposed fix: `setup-checklist.md` and `trackers/linear.md` step 3 add "one `project:<slug>` label per context pack".
3. *Linear links are not in the body.* Linear carries a linked document in `attachments`, not the description; the contract's `read_issue` returns title, body, labels, comments, and the protocol reads inputs from "the pack or the issue's own links". A Doc attached the Linear way would be invisible. Proposed fix, in the contract: `read_issue` returns the issue's links (title and URL) as part of the body, and each implementation says where they come from (`attachments` on Linear; body text on local markdown).
4. *The digest has no home* (carried from ticket 02): printed to the operator, not posted. Same proposed fix as before: a standing pass-log issue per team, when the digest becomes the daily post in stage 2.
5. *`plan` and `digest` are hand-composed on Linear.* On the local tracker `apm.triage` computes candidates and the digest; on Linear the agent composes both from `list_issues` and `list_comments`. Not a behaviour gap, but the idempotency and candidate rules are followed by reading, not enforced by code. The stage 2 GraphQL implementation closes this.

The signature convention worked as designed: every comment shows `author: Hannah Theis` and is recognised as the agent's by its `-- apm` line.

Further gaps found:

6. *Answers given in chat do not reopen a needs-info issue mechanically.* `apm.triage.plan` reopens `apm:needs-info` only on a human-authored comment after the questions. The agent's `#### Answers received` comment is agent-authored, so on the local tracker it would not reopen the issue; here the agent reclassified in the same pass, so nothing was missed. Proposed fix, in the protocol: a chat answer is written back as the agent comment **and** treated as reopening by the pass that records it (no separate rule needed if the recording pass always reclassifies immediately, which this one did; write that down).
7. *Project labels created by the agent.* `project:<client>` was created through the connector on Hannah's say-so, as the `apm:` labels were on 12 September. The contract says the boundary never creates labels; this was an operator step performed by the agent, not a boundary write.
